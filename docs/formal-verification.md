# Formal verification

Selected functions of kalyx are to be proved in Lean 4: Charon extracts the
Rust source of the library, Aeneas translates the extraction into Lean
definitions, and hand-written proofs show that those definitions satisfy
independently written specifications. The proof tooling that does this is
taken over from krepi at a fixed commit, file by file, as the
[porting record](../PORTING.md) lists; this page describes it as it runs in
kalyx.

Nothing about kalyx is proved. No proof target, statement, model, library
axiom or trusted item is registered, and no code of the library has been
extracted.

## Status

What exists today:

- the commands `cargo xtask formal run`, `guard`, `toolchain-check`,
  `check` and `vectors` ([commands](#commands));
- the `lean` and `subset` steps of `cargo xtask check` and its check of the
  image references of the workflows
  ([checks](#checks-in-cargo-xtask-check));
- the workflow `formal`, which runs the gate in CI on every pull request to
  `main` and every push to `main`, in a job that is not required
  ([CI job](#ci-job));
- the Lake project in `verification/` with the qualification proofs, the
  qualification crate and its cases, the reviewed external declarations,
  the tool manifest, the Aeneas patch, the image pin and the registries,
  which are empty ([layout](#layout));
- the module list in the contracts of the components that are to become
  proof targets ([module list](#module-list)).

The gate runs the [qualification](#qualification) of the pinned tools and
the [base round](#base-round), which builds, audits and replays the
hand-written Lean: today the qualification proofs and the definitions that
they use. `cargo xtask formal check` reports every production function of
the files of the module list, since no target is registered and no contract
lists an open obligation yet; it is not part of `cargo xtask check` or of
the gate. Proof targets, specifications, statements and the other parts of
the gate are planned, and this page changes with them.

## Tools

The proof tools have one set of pinned versions for two hosts:
`linux-aarch64`, where CI runs them in a container image on a GitHub-hosted
`ubuntu-24.04-arm` runner, and `darwin-arm64`, whose column of the manifest
names a local installation at `artifacts/formal/tools`, which this
repository does not provide. Only runs in the image are evidence.

The image is the one that krepi builds and publishes,
`ghcr.io/casxi-lab/krepi-formal`, taken by the digest that
`verification/image-pin.json` pins; kalyx does not build images. Its tools
are installed below `/opt/krepi-formal`, the prefix of the `linux-aarch64`
column, and its `versions.json` records what it holds. On `linux-aarch64`,
`cargo xtask formal run` compares that record with the tool manifest and the
reference of the image that the job names with the pin before any tool
runs, and refuses to run as a user that is root or can write the
installation.

`cargo xtask formal toolchain-check --aeneas DIR --charon DIR` checks
checkouts of Aeneas and Charon and the Aeneas patch against the manifest:
the Lean toolchain that Aeneas names, the Charon commit of its `charon-pin`,
the Rust nightly of Charon's `rust-toolchain`, the digests of the patch and
of the Lake lock of the Aeneas Lean library and its Mathlib commit, the
commits of both trees, the Lean archive of each host, the Rust targets (the
extraction triple `aarch64-unknown-linux-gnu`, the triple of the image's
host, needs none) and the two host columns. Each tool command of the gate
runs with exactly the variables that the gate gives it: offline Cargo with the Cargo and rustup
homes of the installation, Lake's artifact cache turned off, Git without
system or global configuration, a `PATH` of the installation and the system
directories, and a home and a temporary directory of the run.

## Commands

| Command | What it does |
| --- | --- |
| `cargo xtask formal run [--target NAME]...` | Runs the proof gate on a snapshot of the gate inputs and writes its receipt ([gate run](#gate-run)); with `--target`, runs only the named targets, of which none is registered |
| `cargo xtask formal guard --event PATH` | Checks a pull request, given by the JSON of its `pull_request` event, against the rules for changes of statements, proofs, sources and the module list ([guard](#guard)) |
| `cargo xtask formal toolchain-check --aeneas DIR --charon DIR` | Checks Aeneas and Charon checkouts and the Aeneas patch against the tool manifest ([tools](#tools)) |
| `cargo xtask formal check [--write]` | Checks that every production function of the files of the module list is in the `proves` or `unclosed` list of a target or in `verification/open.json`, that this file is what the contracts give, and that the registries hold nothing that the gate does not support; `--write` first writes `open.json`. It runs no tool and proves nothing |
| `cargo xtask formal vectors [COMPONENT]` | Replays the test vectors of a component, or of each component whose contract names a replay, through its specification with the pinned Lean and compares the results line by line with its host results ([test vectors](#test-vectors)); no contract names vectors yet |

`cargo xtask formal` alone lists these commands. `cargo xtask check` does
not run the gate, which needs the pinned tools.

## Checks in cargo xtask check

The `lean` step reads each tracked `.lean` file below `verification/`, which
must be a UTF-8 regular file, and `verification/tcb.json`, and applies the
[source rules](#source-rules).

The `subset` step reads the files of the [module list](#module-list), apart
from those that the targets of the root package reach only as test code,
and reports, with its file and line, each `static mut`, each use of an
interior-mutability type (`Cell`, `RefCell`, `UnsafeCell`, `OnceCell`, or a
path through `cell` or `atomic`), each `cfg` attribute but `#[cfg(test)]`
in exactly this form on a module, and each macro that holds one of these
names, `cfg` or `static`. It reads the targets from
`cargo metadata --format-version 1 --locked --offline --no-deps --manifest-path Cargo.toml`.
Each TOML file in a directory named `compile-fail` is a compile-fail case,
with the fields `file`, `find`, `replace` and `error`: the step builds a
copy of the tracked files with `cargo check`, which must succeed, and a copy
with the case applied, which must fail with the error code `error`. There is
no case yet. Files outside the module list are not checked.

The `workflows` step also requires that one of the workflows that run on
pull requests names the image of `verification/image-pin.json` by its
reference, and that every mention of the image's repository in them is that
reference.

## Gate run

`cargo xtask formal run` runs the gate on the commit checked out and writes
a receipt of the run, whether it passes, fails or stops on an internal
error.

### Gate inputs and snapshot

The gate inputs are `Cargo.toml`, `Cargo.lock` and `src/` of the root
package, which is the input of extraction, `.cargo/config.toml`,
`verification/`, `xtask/`, `.github/workflows/` and `rust-toolchain.toml`.
A run

1. takes the snapshot: the commit checked out, its root tree and the Git
   object of each gate input, or none for a gate input that the commit does
   not have;
2. stops unless no gate input has a staged or unstaged change or an
   untracked file that Git does not ignore;
3. exports the gate inputs of the snapshot commit with `git archive` into
   `work/source` and checks that the export holds every file with its mode
   and object name, so that attributes such as `export-ignore` cannot change
   what the run reads; the tool manifest of the export must be the one that
   the run read at its start, the image is checked on `linux-aarch64` as
   [tools](#tools) says, and `verification/targets.json` must register every
   name given with `--target`;
4. rejects the run when a gate input is a Python source, a Lean file below
   `verification/KalyxGen/`, the directory of the generated definitions, or
   a Cargo configuration in a directory other than the root;
5. fails when Cargo would read a Cargo configuration in the export, or in a
   directory above it, other than the snapshot's own `.cargo/config.toml`;
6. checks the root package from the `Cargo.toml` and `Cargo.lock` of the
   export alone, without running Cargo or reading the sources of its
   dependencies: the lock must hold the package that the manifest names and
   no other package without a source, and its registry packages must be
   exactly those that `guard/crates.txt` of the snapshot commit lists, which
   the run reads through Git. A package from another source, a package of
   the lock that the list does not name and a name of the list that the lock
   does not hold reject the run.

Every later step reads the gate inputs from the export. At the end the run
takes the snapshot again: a gate input whose object differs, or that is not
clean, makes the run `STALE`.

### Deadlines and processes

Each command runs in a process group of its own, with its input from a file
or from nothing and its two output streams written to files of `logs/`. Its
limit is the smallest of the cap of its call site (1,800 s for Charon,
3,600 s for Aeneas, 7,200 s for each `lake build` and 1,800 s for each
`lake env lean`; none for `leanchecker` and Git), the rest of the budget of
its phase and the rest of the gate's budget of 7,200 s. The steps after the
phases have 300 s more. When a command ends or reaches its limit, the run
kills its process group; a process of the group that is still there 60 s
later makes the command a tool failure. SIGINT and SIGTERM, and SIGHUP
unless it was ignored, stop the run: it kills the group of the running
command and ends by the same signal, without a receipt.

### Extraction

An extraction runs Charon on a crate of the export, with the roots and the
opaque items that it is given, and Aeneas on Charon's output, in a work
directory of its own with a Cargo target directory of its own.
`verification/extraction.toml`, schema 1, says how Charon compiles each
crate: the qualification crate for the host, with a triple recorded for each
host of the tool manifest and no features or `cfg` settings, and the root
package, in `[package]`, for `aarch64-unknown-linux-gnu` with no features
and no `cfg` settings. A configuration that the gate cannot follow stops the
run. No target is registered, so nothing of the root package is extracted.

### Qualification

The qualification phase checks the pinned tools against the code shapes of
the qualification crate, `verification/qualification/`, before anything
relies on them; every run has it, with a budget of 3,600 s. The crate
depends on no crate and is a workspace of its own. Each case of
`verification/qualification/cases.json` names a module below `KalyxGen`,
the roots of its extraction and whether it is to translate, to translate
into ill-typed Lean or to be rejected, with the exact diagnostics, external
functions and types and, where it records them, loops of its extraction. A
case may name reviewed external declarations below `verification/externals/`
and theorems below `Kalyx.Qualification` that it proves about its
translation. Each case is a unit of the run: it is extracted, compared with
its expectation and, unless it expects a rejection, built in a Lake stage of
its own. Each theorem of a case is a unit too, built and audited.

### Base round

The base round builds, audits and replays the hand-written Lean of the
snapshot with the generated modules of the qualification cases that have
proofs, in a stage of its own, with a budget of 3,600 s. It rejects the
round when `statements.json` records another statement hash than that of
the snapshot, and checks every `.lean` file of the snapshot against the
[source rules](#source-rules). It writes the root module `Kalyx`, which
imports every module below `Kalyx` and `KalyxGen` of the stage, builds it
with `lake build --no-cache --wfail`, audits the axioms of every theorem
with `lake env lean`, replays the build with `leanchecker` and counts the
heartbeats of each own file with theorems. Its units are `base` and one for
each statement registered as proved, of which there is none.

### Source rules

The rules of the `lean` step and of the base round read Lean's tokens, so
comments and string literals do not count:

- a file lies below `verification/Kalyx/` or `verification/externals/` and
  is a module file: its header starts with `module`;
- `native_decide`, `bv_decide` and the option `native` of `decide` appear
  only in a file that a `native-decision` item of `verification/tcb.json`
  names;
- `axiom` appears only below `verification/externals/`;
- a file of the statement side imports neither the root module `Kalyx` nor
  a module below `Kalyx.Proofs`.

### Guard

`cargo xtask formal guard --event PATH` checks a pull request against the
rules below. `PATH` is the JSON of a `pull_request` event as GitHub writes
it; the guard reads the base and head commits, the names of the labels and
the description, and runs Git itself in the repository root without the
caller's Git variables and configuration. It prints `PASSED <rule>` or
`FAILED <rule>: <why>` for each rule, the labels and the statement hash of
the head, and exits with 0 when every rule holds and with 1 when a rule
fails or an input cannot be read.

From the merge base of the two commits to the head, the guard finds the
changed paths of the statement side, the proof files (the `.lean` files
below `verification/Kalyx/Proofs/`) and the sources (the `.rs` files below
`src/`); the statements no longer proved and those added, removed or
renamed in `statements.json`; the newly raised heartbeat limits in the
changed files of the statement side and proof files; and the entries of the
[module list](#module-list) at the merge base that the head no longer lists.

The description gives these fields, each on a line of its own as
`Name: value`; a field given twice, or with a value of another form, counts
as missing. The ids are opaque, and the records that they name are kept
outside this repository. The pull request template,
`.github/pull_request_template.md`, ends with the fields of this table but
`Module-List-Approval`, empty.

| Field | Value |
| --- | --- |
| `Review` | The id of the review of a statement change: 1 to 64 ASCII letters and digits |
| `Approval` | The id of the approval of the change, in the same form; [CONTRIBUTING](../CONTRIBUTING.md#proof-fields) says what it names for a component at tier A2 |
| `Approved-Statement-Hash` | The statement hash that was approved, 40 lowercase hexadecimal digits |
| `Heartbeats-Review` | The id of the review of a raised heartbeat limit |
| `Phase` | `statement`, `proof` or `rewrite` |
| `Author` | The opaque id of the author |
| `Module-List-Approval` | The id of the owner's approval of a removed or narrowed entry of the module list |

The labels are `spec` for a change of statements, `proof` for a change of
proofs, and `ai-proof` for proofs that an AI system wrote, which the guard
records without judging it.

| Rule | Fails when |
| --- | --- |
| `statement-change-needs-spec` | A path of the statement side changed, or a statement is no longer proved, and the label `spec` is missing |
| `spec-approval` | The label `spec` is present and `Review`, `Approval` or `Approved-Statement-Hash` is missing, or the approved hash is not the statement hash of the head |
| `no-sources-with-proofs-or-statements` | A source changed together with the label `proof`, a changed proof file or a changed path of the statement side |
| `heartbeats-need-review` | A heartbeat limit is newly raised and `Heartbeats-Review` is missing |
| `phase-and-author` | The label `spec` or `proof` is present and `Phase` or `Author` is missing or malformed |
| `proof-of-registered-statements` | A statement is added, removed or renamed and the label `spec` is missing |
| `module-list` | An entry of the module list at the merge base is not an entry at the head, because it, its block, its section or its contract was removed or it was made narrower, and `Module-List-Approval` is missing; a new entry needs no approval |

On a pull request, `cargo xtask formal run` runs the same check through the
gate's Git in a first phase, `guard`, and records it in the receipt; a rule
that fails there does not change the status of the run.

### Results

Every command of the gate gets one class from one function,
`outcome::classify`, which every call site uses: `PASSED`, `PROOF_FAILURE`,
`TOOL_FAILURE` or `NOT_RUN`, and `BUDGET`, a tool failure at the limit of a
phase or of the gate rather than at the cap of the call site. A tool failure
is never a statement about the code. The conventions:

| Result of the command | Call sites | Class |
| --- | --- | --- |
| Ran until its cap | All | `TOOL_FAILURE` |
| Ran until the rest of a budget | All | `BUDGET` |
| Ended by a signal | All | `TOOL_FAILURE` |
| Exited with a status above 128 | All | `TOOL_FAILURE` |
| Prints `error: Lean exited with code N` with `N` above 128 | The builds and the audits | `TOOL_FAILURE` |
| Charon exits with 255 | Charon | `TOOL_FAILURE` |
| Cargo reports a process ended by a signal, as in `(signal: 9, SIGKILL: kill)` | Charon | `TOOL_FAILURE` |
| Could not start or could not keep its output | All | `TOOL_FAILURE` |
| Ended by itself, and an output file that the gate reads, `translation.json` or a generated Lean file, cannot be read or is not what the tool writes, or `translation.json` is missing after an exit with 0 | Aeneas | `TOOL_FAILURE` |
| The base build fails with errors or warnings in kalyx's own modules | The base build | `PROOF_FAILURE` |
| The base build fails without an error or a warning in kalyx's own modules | The base build | `TOOL_FAILURE` |
| The comparator exits with 1 and prints a line that starts with `error: Child exited with ` | The comparator | `TOOL_FAILURE` |
| The comparator exits with 1 otherwise | The comparator | `PROOF_FAILURE` |

A process of the group that survives the kill is a tool failure as well, and
so is any failure of Git, which the gate runs itself, and any status of the
comparator but 0 and 1. Any other non-zero status of a tool is a
`PROOF_FAILURE`, which its call site compares with what it expects. The call
sites are Charon and Aeneas, the qualification builds, the ill-typed builds
and the case audits of the [qualification](#qualification), the base build,
the axiom audit and `leanchecker` of the [base round](#base-round), and the
comparator, which no phase runs yet.

kalyx's own modules, in the rows of the base build, are every module below
`Kalyx` but the root module, and the reviewed external declarations
installed for qualification cases. A message counts for them when its
`error:` or `warning:` line names the file of one of them; a message in a
generated file, Lake's own `error: build failed`, a `trace:` line and a
message without a position do not.

A command that does not start because the command before it did not write
what it needs, such as Aeneas after a Charon that failed, is `NOT_RUN` with
the reason `not started:`. It decides nothing: the command before it does.
A command whose limit is used up before it starts is `NOT_RUN` for the
budget.

A unit is a registered piece of work that gets exactly one conclusion: a
qualification case, an audited theorem, the base round. A unit with a
command that was a tool failure is concluded `TOOL_FAILURE`, and one with a
command that met a budget, or did not start because its limit was used up,
`BUDGET`, whatever its phase concludes. The status of a run is the first of
`TOOL_FAILURE`, `BUDGET`, `STALE` and `REJECTED` that its failures and the
conclusions of its units give, `TOOL_FAILURE` when a unit is `NOT_RUN` and
none of these is given, `SCOPED` for a run of named targets, and otherwise
`VERIFIED`. A run of the whole gate is complete when its only
failures are `STALE` and no unit is `NOT_RUN` or `BUDGET`.

The command exits with 0 for `VERIFIED` and `SCOPED` and with 1 for any
other status, printing each failure on standard error; with 2 on a usage
error; and by the signal after a stop signal. When the receipt cannot be
written, it writes the receipt to standard error and exits with 120.

### Receipt

`receipt.json`, schema 2, records the trigger of the run, the host and, on
`linux-aarch64`, the image, the snapshot commit and tree with the objects of
the gate inputs at the start and at the end, the budgets, the resources,
each phase with its time, each unit with its conclusion, every command with
its call site, class, limit and output files, the qualification, the base
round, the guard on a pull request, and the failures. It is the pretty form
of `serde_json`, with its fields in this order and every map sorted by its
keys; times are seconds, rounded to milliseconds.

| Field | Content |
| --- | --- |
| `schema` | `2` |
| `command` | `cargo xtask formal run` |
| `status` | `VERIFIED`, `REJECTED`, `STALE`, `TOOL_FAILURE`, `BUDGET` or `SCOPED` |
| `complete` | Whether the run is complete, as [results](#results) defines it |
| `trigger` | `mode`, `MANUAL` for a run of the whole gate and `SCOPED` for a run of named targets; `event`, `ref`, `run_id` and `attempt`, from `GITHUB_EVENT_NAME`, `GITHUB_REF`, `GITHUB_RUN_ID` and `GITHUB_RUN_ATTEMPT`, or `null` |
| `targets` | The names given with `--target`, sorted; empty for a run of the whole gate |
| `host` | `linux-aarch64` or `darwin-arm64`, or `null` on another host |
| `image` | On `linux-aarch64`, the reference in `KALYX_FORMAL_IMAGE`, the user ID of the run, whether it could write the installation, and the text and SHA-256 of `versions.json` and the text of `/etc/os-release`; `null` on another host |
| `run`, `directory` | The identifier of the run, and its directory relative to the repository root |
| `started`, `seconds` | The Unix time in seconds at which the run started, and how long it took |
| `commit`, `tree` | The snapshot commit and its root tree, or `null` |
| `inputs` | `before` and `after`, the object of each gate input at the start and at the end, or `null` when they were not taken; `clean_after`, whether the gate inputs were clean at the end, or `null` |
| `budgets` | `gate_seconds`, 7200, and `receipt_margin_seconds`, 300 |
| `resources` | The disk space of the run directory, the largest resident set of one process and the memory peak of the run's cgroup, each `null` when the host does not report it |
| `phases` | For each phase, `budget_seconds`, `seconds` and `ran` |
| `units` | For each unit, its `phase`, its `status` and the `reason` for it, or `null` |
| `qualification` | What the qualification found, or `null` when it did not start |
| `base` | What the base round found, or `null` when the round stopped before it recorded it |
| `guard` | What the [guard](#guard) found on a pull request, or `null` without a pull request event or when its phase did not finish |
| `commands` | Every command, in the order in which they ran, with its sequence number, phase, unit, call site, arguments, working directory, class and reason, exit status or signal, whether it ran until its limit, the limit and what set it, its time, whether processes of its group survived the kill, and its output files |
| `failures` | Every failure that is not the conclusion of a unit, with its `status` and `message` |

## CI job

The workflow `formal`, `.github/workflows/formal.yml`, has one job,
`formal run`. It runs on every push to `main` and on every pull request to
`main` when it is opened, reopened or updated, when a label is added or
removed and when its description is edited, since the guard reads the labels
and the description; a manual run of the workflow runs no job. It is not a
required check. It runs on a GitHub-hosted `ubuntu-24.04-arm` runner, may
only read the repository's contents and uses no stored credentials. It
checks out the candidate commit with its history, records the runner, pulls
the image by the digest that the workflow names, builds xtask on the runner
and probes a container of the image with the flags of the gate, which must
run as a user other than root on a read-only file system, without
capabilities, new privileges or a network, and must not be able to write the
installation. On a pull request it then runs `cargo xtask formal guard` and
the vectors step; finally it runs `cargo xtask formal run` in a container of
the image with the checkout mounted. It writes a summary of the receipt and
uploads the receipt, the logs and the outputs of the steps as the artifact
`formal-receipt-<commit>-<attempt>`. The job may take 153 minutes: 15 for the
steps before the vectors step, the 13 of the vectors step, and the gate's
7,200 s with the 300 s of its receipt.

### Vectors in CI

The vectors step only replays the fixture of xtask. On a pull request that
changes `Cargo.toml`, `Cargo.lock`, `src/`, `verification/`,
`docs/components/`, `xtask/` or `.github/workflows/formal.yml` since the
merge base, it builds the test executable of xtask, within 5 minutes, and
runs its ignored test
`formal::vectors::tests::the_fixture_replays_with_the_pinned_lean` in a
container of the image, within 6 minutes and one more for the kill of the
container, which is removed when it ends; otherwise it prints that it
compares 0 components. It runs no host tests and no
`cargo xtask formal vectors`. Its failure fails the job, and the gate still
runs.

## Module list

The module list names the files that are to become proof targets, the
proof-target modules. The contract of a component,
`docs/components/<name>/contract.md`, may hold in its `Extractability`
section a fenced block with the info string `paths`, whose lines are
repository paths of a tracked `.rs` file or of a directory that holds one;
a line that names no tracked `.rs` file is a problem. The list holds the
term core, the coefficient-field trait, the polynomials, the errors and
result states, the accounting core of the context and the function registry,
as the contracts of the
[terms](components/terms/contract.md#extractability),
[numbers](components/numbers/contract.md#extractability),
[polynomials](components/polynomials/contract.md#extractability),
[errors](components/errors/contract.md#extractability),
[context](components/context/contract.md#extractability) and
[function registry](components/registry/contract.md#extractability)
components state. Files outside the list are neither checked by the
`subset` step nor inventoried. The `module-list` rule of the
[guard](#guard) lets an entry be removed or narrowed only with an approval;
a new proof-target module adds its entry in the same change.

`cargo xtask formal check` inventories the production functions of these
files: from the targets of the root package, which `cargo metadata` gives,
it follows the `mod` declarations of the source and keys each function that
production code reaches as `<file>#<name>`, with the owner of a method. Each
must be in the `proves` or `unclosed` list of a target or be covered by an
open obligation. The open obligations are the rows of the tables
`Open obligations` of the contracts, with the columns `Obligation`, `Kind`,
`Verified state`, `Carrier` and `Stage`; an obligation names a file, a
function of a file or a directory within an entry of the module list, and
its stage, the release by which it is to be closed, is 0.3 at the latest.
`verification/open.json` holds them as `cargo xtask formal check --write`
generates them, and a file that differs fails the check.

## Statements and proofs

The statement side is the hand-written part of the Lake project that decides
what statements mean: every tracked `.lean` file below `verification/`
outside `verification/Kalyx/Proofs/`, the registry of library axioms
`verification/axioms.json`, and the Lake project files
`verification/lakefile.*`, `lean-toolchain` and `lake-manifest.json`. The
statement hash of a commit is the Git tree of exactly its paths of the
statement side; `verification/statements.json` records it and is not on the
statement side itself. In a checkout of a commit, these commands print it:

```sh
(
  export GIT_INDEX_FILE="$(mktemp -d)/index"
  git read-tree HEAD
  git rm -r --cached --quiet -- . \
    ':(exclude,glob)verification/**/*.lean' \
    ':(exclude)verification/axioms.json' \
    ':(exclude,glob)verification/lakefile.*' \
    ':(exclude)verification/lean-toolchain' \
    ':(exclude)verification/lake-manifest.json'
  git rm -r --cached --quiet --ignore-unmatch -- verification/Kalyx/Proofs
  git write-tree
)
```

A change of the statement side changes the hash: the base round rejects a
snapshot whose `statements.json` records another, and the guard requires the
label `spec` and an approval of the new hash.

## Test vectors

A contract names its vectors in its section `Legacy test vectors`, in a
fenced block with the info string `vectors` that gives, in TOML, the vector
file as `vectors` and, once it exists, the replay module of the statement
side below `Kalyx` as `replay`. `cargo xtask formal vectors` builds the
replay module in a stage of a run directory, runs it on the vector file with
the pinned Lean, and compares its result lines in order with the host
results in `artifacts/formal/vectors/<component>.results`. No contract has
such a block, and no test of the library writes host results yet.

The fixture of the tests, in `xtask/src/formal/fixtures/vectors/`, is a
replay of the sum of two natural numbers with its vectors and results. A
local replay with the pinned Lean needs the `darwin-arm64` installation at
`artifacts/formal/tools`:

```sh
cargo test --manifest-path xtask/Cargo.toml --bin xtask -- --ignored --exact \
  formal::vectors::tests::the_fixture_replays_with_the_pinned_lean
```

## Provable subset and design rules

Code of a proof-target module is written in the subset of Rust that Charon
and Aeneas translate, by the constructs, loop shapes and design rules of the
[krepi convention on the provable subset](https://github.com/casxi-lab/krepi/blob/73b8aaa97c45c5d20c490a541d302ccdb5eae311/docs/conventions/provable-subset.md)
that the contracts cite; the `subset` step checks the parts of it that a
scan of the source can check, and review checks the rest. Two of its design
rules are met as follows:

- **Rule 2, no allocation at run time.** The context is an accepted
  deviation: its accounting core allocates its frame table at run time, as
  the [context contract](components/context/contract.md#extractability)
  states, and a proof of it will need models of `Vec` and `Box`.
- **Rule 8, no interior mutability.** The `AtomicBool` of the cancellation
  flag `CancelFlag` is the only atomic or cell type in the non-test code of
  the library. It lies in the observer adapter `src/context/observer.rs`,
  which is not in the module list and which the extraction is to cut; the
  `subset` step checks that the files of the module list use none.

## Limitations

- The image and its tools are krepi's, taken by digest; a change of a tool
  needs a new image from krepi.
- The gate's CI job is not required, and no receipt decides whether a change
  may be merged.
